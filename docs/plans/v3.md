# v3 — "The store" (branch `v3`, from `main`)

Backlog entry this executes: **Deferred — SQLite store (ttd 133)** in `docs/FUTURE.md`.
That entry's verdict still holds: this is not for performance. It is for row-level writes,
which is what concurrent external edits, a persistent op log and multiple graphs all need.

## Slice 1 — parity, safely (DONE)

Goal: SQLite becomes the store with **no observable change** to the app, and no possibility
of losing or altering an existing task.

Shipped:
- `cmake/deps.cmake` — SQLite 3.53.4 amalgamation via FetchContent, pinned by SHA256. Chosen
  over system `libsqlite3` so the system requirement stays "X11 + GL dev headers".
- `model/Store.hpp` — one seam, two backends. `load`/`save` dispatch on the path's extension
  (`.db`/`.sqlite`/`.sqlite3` → SQLite, else JSON), so `App` and its 12 `save()` call sites
  are untouched. `loadJson`/`saveJson`/`loadDb`/`saveDb` remain callable explicitly.
- `model/SqliteStore.cpp` — one row per task + `meta(next_id)`, WAL, `synchronous=NORMAL`,
  3 s busy timeout. `roots`/`children` are **derived**, not stored: `ord` is position among
  siblings and parent = 0 is top-level. Save is one `BEGIN IMMEDIATE` transaction: upsert
  every node, remove rows no longer in the forest, write `next_id`. (Slices 3–5 below evolved
  the schema to version 3; see them for its current shape.)
- `Forest`/`Task.hpp` — `tt::equivalent(a, b)`: exact deep equality (ids, `nextId`,
  root/doneRoot order, every field, children order). Pure, in `tt_core`.
- `main.cpp` — migration on first run only: JSON → DB, read the DB back, require
  `equivalent()`. On any failure the partial DB (and its `-wal`/`-shm`) is deleted and the app
  **stays on JSON**. `tasks.json` is only ever read — never written, renamed or removed — so
  it remains a complete pre-switch backup.
- `tests/store_tests.cpp` — round-trip of a forest exercising every field, both root
  orderings, DONE subtrees, re-save idempotence, row deletion after `removeSubtree`, backend
  dispatch, and the migration's three refusals (existing DB, missing source, failed verify).
  Plus an opt-in real-data check: `TASKTREE_TEST_JSON=<copy of tasks.json> ./build/store_tests`.

Verification run: 78 checks / 0 failures; `ctest` green. Against a copy of the live
`tasks.json` (134 tasks, 6 roots, 56 DONE roots, `nextId` 137) the migration verified, and the
resulting DB was **independently** re-read with Python's `sqlite3` — every field, parent link
and sibling order matched the JSON, `next_id` included.

## Slice 2 — incremental writes (DONE)

`saveDb` takes an optional `baseline`: the state this process last wrote or loaded. With one,
it writes only the difference — and, the load-bearing part, it infers a deletion from *present
in baseline, gone from the forest* rather than from *absent from the forest*. Rows in neither
belong to somebody else and are left alone. `App` holds that baseline as `lastSaved_`, seeded
from the forest as loaded (seeding it empty would leak deleted rows on the first save) and
advanced only on a successful write, so a failed save retries in full.

`ord` is compared as well as the columns: removing a middle child renumbers its later siblings
without changing a single field on their rows. `next_id` is written as
`MAX(existing, ours)` — another writer may have taken ids past ours, and lowering it would
hand out an id already in use.

Measured on a copy of the live 134-task store, counting real row writes with triggers:

| save | row writes to `tasks` |
|---|---|
| nothing changed | **0** (was 134 upserts + 134 id reads) |
| one task edited | **1** update |
| one task added | **1** insert |
| 9-node subtree deleted | 9 deletes + 11 updates — exactly the later siblings whose `ord` shifted |

Tests cover edit/insert/delete/ord-shift, plus two `Forest`s standing in for two processes:
the external writer's task survives the app's save, and the same save *without* a baseline
still drops it — so the mechanism is load-bearing rather than incidental.

## Slice 3 — soft delete (DONE)

**Nothing is ever hard-deleted.** There is no `DELETE` statement anywhere in
`SqliteStore.cpp`. Schema version 2 adds `tasks.deleted_at` (epoch ms, 0 = live); removing a
task stamps it and the row stays forever. Loads filter `deleted_at = 0`, so a `Forest` still
only ever holds live tasks — the trash stays out of the model and is read through
`store::deletedRows()`, which is also the foundation for a future "restore deleted" view.

- Writing a task sets `deleted_at = 0` on both the insert and the conflict path, so an id that
  comes back (undo of a delete) revives its row rather than duplicating it.
- The stamp is applied `WHERE deleted_at = 0`, so a repeated delete keeps the *first*
  deletion's timestamp.
- **Schema upgrades are additive and tested.** `upgradeSchema` reads `user_version` and
  `ALTER TABLE ADD COLUMN`s its way forward — instant, and no existing row is rewritten or
  dropped. A DB written by a *newer* build is refused rather than corrupted. `store_tests`
  builds a v1 fixture by hand (it links `sqlite3` for this, and to inspect rows the API
  hides) and asserts the rows, parent links and `next_id` all survive.

Verified on a v1 DB built from the live data: 134 rows before, `user_version` 1 → 2, 134 rows
after, all marked live. Deleting a 9-node subtree left the table at 134 rows with 9 stamped.

## Slice 4 — done is a flag, not a move (DONE)

`markDone` used to `detachFromParent` and push onto a second root list (`Forest::doneRoots`),
which threw the task's position away: `restoreFromDone` could only drop it back at the top
level. The DB couldn't fix that — `parent` was already 0 before the store ever saw the row.

So `markDone` now only sets `Task::done`. The task keeps its parent **and its sibling index**,
which means un-doing needs no stored memory of where it was: it never left. `doneRoots` is
gone; the DONE section is derived by `Forest::doneSectionRoots()` (done tasks whose parent
chain holds no other done task), and `isInDoneSection` is now simply "is any task on my
parent chain done" — shorter than the list-membership version it replaces.

This makes a **done child of a live parent** a first-class case: it heads its own DONE entry
while sitting in place under its parent, and un-doing returns it to that exact slot.

Consequences, all of them found by the tests or by grepping for the old invariant:
- `TidyLayout` filters done tasks out of both walks (`Walker::kidsOf`, plus a live-roots pass)
  — `roots[]` now includes done top-level tasks.
- `DevRoute::ensureDevRoot` relied on a done "tasktree dev" root being absent from `roots`;
  without an explicit `!done` check it would have resurrected a completed dev node. The
  existing test caught this.
- `App::buildTreeOutline` (the classifier's view of the canvas) would have offered DONE tasks
  as candidate parents.
- `DragController` would have given a done sibling a slot in the drop preview, despite it
  having no rect.
- `saveJson` drops the `doneRoots` key (format version 2); `loadJson` still reads it and
  merges it into `roots`, so existing files keep working.
- **The SQLite schema did not change** — only the interpretation of a row. Old DBs load as-is.

Verified on the real data: 134 tasks → 62 top-level (6 old roots + 56 old `doneRoots` merged),
56 derived DONE entries, 59 canvas tasks. Cross-checked with Python against the JSON: every
former `doneRoot` maps to exactly one derived DONE entry, nothing lost.

One behaviour change worth knowing: deleting a live parent now also deletes its done children
(they are its descendants again). Previously they had been detached and would survive. With
soft delete they are recoverable either way.

## Slice 5 — no booleans: `done` folded into `done_at` (DONE)

`done` (bool) and `done_at` (timestamp) were two representations of one fact, kept in sync by
convention across the model and `App`. Both desync states were representable and meaningless.
`deleted_at` already showed the better shape, so completion now matches it: **the timestamp is
the state.**

    done_at = 0   not done          deleted_at = 0   live
    done_at > 0   done, at that ms  deleted_at > 0   deleted, at that ms
    done_at = -1  done, date unknown  (kDoneAtUnknown)

`Task::done` is gone; `Task::isDone()` is `doneAt != 0`. `markDone(id, whenMs)` takes the
completion time, since the model owns no clock — the same shape as `addTask`'s `createdAt` —
and `App` no longer sets `doneAt` in a second step afterwards.

**The sentinel is not decoration.** 43 of the live store's 56 done tasks were completed before
the date was recorded: they are `done = 1, done_at = 0`. Treating "done" as `done_at > 0` would
have silently un-completed all 43 and dumped them back onto the canvas. `kDoneAtUnknown`
records "done, when unknown" without inventing a completion date, and since nothing renders the
date (it only drives the DONE panel's sort) negatives sort exactly where 0 used to.

Both legacy paths backfill at the point old data enters:
- `loadJson` — a `"done"` key present with `doneAt` 0 becomes `kDoneAtUnknown`; a `doneAt` on a
  not-done row is cleared. `saveJson` no longer writes `"done"`.
- `upgradeSchema` 2 → 3 — the same two `UPDATE`s, *then* `ALTER TABLE tasks DROP COLUMN done`.
  The order matters: dropping first would destroy the only evidence those 43 were done.

Also updated: `scripts/ttd-scan.sh` read the `done` column (it now reads `done_at`, and filters
`deleted_at = 0`, which it should have done since slice 3).

Verified end to end on the live data:
- Fresh JSON → DB: was-done set (56) == is-done set (56), 13 dated + 43 `-1`, none lost, none
  invented, `done` column absent, `user_version` 3.
- An existing v2 DB *with* the column (56 `done=1`, only 13 dated): after opening, 134 rows
  intact, column gone, 56 rows with `done_at != 0` of which 43 are `-1`.
- The v1→3 fixture in `store_tests` covers dated-done, undated-done and a not-done row carrying
  a stale timestamp.

## Not yet done

1. **The app does not notice external writes.** Clobbering is fixed; staleness is not. The
   app's in-memory forest is a snapshot, so another writer's change is invisible until
   restart, and a task the app subsequently edits is overwritten from memory. Needs a reload
   trigger — `sqlite3_update_hook` is in-process only, so poll `PRAGMA data_version` on the
   event loop or watch the file. This is what finally retires the ttd `stop → edit → start`
   dance (`CLAUDE.md` step 3 still requires it, for this reason and no longer for clobbering).
2. **Op log** (`ops` table) → undo that survives restart; supersedes the in-memory `History`.
3. **Multiple graphs (ttd 106)** — now a `graph_id` column plus a graphs table, not a
   directory of JSON files.
4. **Sibling ordering** — `ord` exists now, so "move among siblings" has a home.
5. **Connection reuse.** Every save still opens the DB, sets pragmas and runs `CREATE TABLE
   IF NOT EXISTS`. Harmless at this size, but a held connection is the natural home for the
   `data_version` poll in item 1.

## Risks / notes

- **One-way door on first launch.** The first run of a v3 binary creates `tasks.db` and stops
  reading `tasks.json`. Nothing is destroyed, but a v1/v2 binary run afterwards would load the
  now-stale JSON and diverge. Migration is deliberately not automated in reverse; JSON export
  covers that direction.
- ~~The ttd workflow reads `tasks.json`~~ **DONE (slice 1a).** `scripts/ttd-scan.sh` now reads
  `tasks.db` when it exists and `tasks.json` otherwise — the same rule as `main.cpp` — and
  names the store it read in its header line, so a stale scan is visible rather than silent.
  It touches nothing: `immutable=1` when the store is idle (a plain `mode=ro` would leave
  `-shm`/`-wal` sidecars behind), `mode=ro` when a `-wal` shows the app is live, and a
  throwaway copy if either fails. `CLAUDE.md` step 1/3 document the DB's derived
  `parent`/`ord`/`done` shape and that edits still require stopping the app.
