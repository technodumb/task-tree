# v3 — "The store" (branch `v3`, from `main`)

Backlog entry this executes: **Deferred — SQLite store (ttd 133)** in `docs/FUTURE.md`.
That entry's verdict still holds: this is not for performance. It is for row-level writes,
which is what concurrent external edits, a persistent op log and multiple graphs all need.

## Slice 1 — parity, safely (DONE)

Goal: SQLite becomes the store with **no observable change** to the app, and no possibility
of losing or altering an existing task.

Shipped:
- `cmake/deps.cmake` — SQLite 3.53.4 amalgamation via FetchContent, pinned by SHA256. Chosen
  over system `libsqlite3` so the system requirement stays "X11 + GL dev headers".
- `model/Store.hpp` — one seam, two backends. `load`/`save` dispatch on the path's extension
  (`.db`/`.sqlite`/`.sqlite3` → SQLite, else JSON), so `App` and its 12 `save()` call sites
  are untouched. `loadJson`/`saveJson`/`loadDb`/`saveDb` remain callable explicitly.
- `model/SqliteStore.cpp` — schema `tasks(id, parent, ord, text, done, collapsed, status,
  created_at, done_at)` + `meta(next_id)`, `PRAGMA user_version = 1`, WAL,
  `synchronous=NORMAL`, 3 s busy timeout. `roots`/`doneRoots`/`children` are **derived**, not
  stored: `ord` is position among siblings, and parent = 0 rows split into canvas vs DONE
  roots by the `done` flag — the rule `Forest::reindexRootsAfterLoad` already used, so no new
  invariant. Roots and doneRoots number `ord` independently. Save is one `BEGIN IMMEDIATE`
  transaction: upsert every node, delete rows no longer in the forest, write `next_id`.
- `Forest`/`Task.hpp` — `tt::equivalent(a, b)`: exact deep equality (ids, `nextId`,
  root/doneRoot order, every field, children order). Pure, in `tt_core`.
- `main.cpp` — migration on first run only: JSON → DB, read the DB back, require
  `equivalent()`. On any failure the partial DB (and its `-wal`/`-shm`) is deleted and the app
  **stays on JSON**. `tasks.json` is only ever read — never written, renamed or removed — so
  it remains a complete pre-switch backup.
- `tests/store_tests.cpp` — round-trip of a forest exercising every field, both root
  orderings, DONE subtrees, re-save idempotence, row deletion after `removeSubtree`, backend
  dispatch, and the migration's three refusals (existing DB, missing source, failed verify).
  Plus an opt-in real-data check: `TASKTREE_TEST_JSON=<copy of tasks.json> ./build/store_tests`.

Verification run: 78 checks / 0 failures; `ctest` green. Against a copy of the live
`tasks.json` (134 tasks, 6 roots, 56 DONE roots, `nextId` 137) the migration verified, and the
resulting DB was **independently** re-read with Python's `sqlite3` — every field, parent link
and sibling order matched the JSON, `next_id` included.

## Slice 2 — incremental writes (DONE)

`saveDb` takes an optional `baseline`: the state this process last wrote or loaded. With one,
it writes only the difference — and, the load-bearing part, it infers a deletion from *present
in baseline, gone from the forest* rather than from *absent from the forest*. Rows in neither
belong to somebody else and are left alone. `App` holds that baseline as `lastSaved_`, seeded
from the forest as loaded (seeding it empty would leak deleted rows on the first save) and
advanced only on a successful write, so a failed save retries in full.

`ord` is compared as well as the columns: removing a middle child renumbers its later siblings
without changing a single field on their rows. `next_id` is written as
`MAX(existing, ours)` — another writer may have taken ids past ours, and lowering it would
hand out an id already in use.

Measured on a copy of the live 134-task store, counting real row writes with triggers:

| save | row writes to `tasks` |
|---|---|
| nothing changed | **0** (was 134 upserts + 134 id reads) |
| one task edited | **1** update |
| one task added | **1** insert |
| 9-node subtree deleted | 9 deletes + 11 updates — exactly the later siblings whose `ord` shifted |

Tests cover edit/insert/delete/ord-shift, plus two `Forest`s standing in for two processes:
the external writer's task survives the app's save, and the same save *without* a baseline
still drops it — so the mechanism is load-bearing rather than incidental.

## Not yet done

1. **The app does not notice external writes.** Clobbering is fixed; staleness is not. The
   app's in-memory forest is a snapshot, so another writer's change is invisible until
   restart, and a task the app subsequently edits is overwritten from memory. Needs a reload
   trigger — `sqlite3_update_hook` is in-process only, so poll `PRAGMA data_version` on the
   event loop or watch the file. This is what finally retires the ttd `stop → edit → start`
   dance (`CLAUDE.md` step 3 still requires it, for this reason and no longer for clobbering).
2. **Op log** (`ops` table) → undo that survives restart; supersedes the in-memory `History`.
3. **Multiple graphs (ttd 106)** — now a `graph_id` column plus a graphs table, not a
   directory of JSON files.
4. **Sibling ordering** — `ord` exists now, so "move among siblings" has a home.
5. **Connection reuse.** Every save still opens the DB, sets pragmas and runs `CREATE TABLE
   IF NOT EXISTS`. Harmless at this size, but a held connection is the natural home for the
   `data_version` poll in item 1.

## Risks / notes

- **One-way door on first launch.** The first run of a v3 binary creates `tasks.db` and stops
  reading `tasks.json`. Nothing is destroyed, but a v1/v2 binary run afterwards would load the
  now-stale JSON and diverge. Migration is deliberately not automated in reverse; JSON export
  covers that direction.
- ~~The ttd workflow reads `tasks.json`~~ **DONE (slice 1a).** `scripts/ttd-scan.sh` now reads
  `tasks.db` when it exists and `tasks.json` otherwise — the same rule as `main.cpp` — and
  names the store it read in its header line, so a stale scan is visible rather than silent.
  It touches nothing: `immutable=1` when the store is idle (a plain `mode=ro` would leave
  `-shm`/`-wal` sidecars behind), `mode=ro` when a `-wal` shows the app is live, and a
  throwaway copy if either fails. `CLAUDE.md` step 1/3 document the DB's derived
  `parent`/`ord`/`done` shape and that edits still require stopping the app.
